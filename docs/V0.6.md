# V0.6 — Durable Audit + Official Windows Lock Integration

## Delivered

- Durable local security-event history in `%LOCALAPPDATA%\SmartLock\security-events.json`.
- Best-effort forwarding of security incidents to the Windows **Application** Event Log.
- Application startup restores the persisted incident timeline.
- Optional Windows workstation locking after the configured application lockout threshold.
- Windows locking uses the official `LockWorkStation` API.
- The application still does **not** read, store, intercept, or validate the Windows password.
- Camera evidence remains explicit opt-in and local-only.

## Policy behavior

The development policy remains:

- 5 rejected attempts → 30-second application lockout.
- If **Lock Windows session after policy lockout** is enabled, SmartLock requests the normal Windows workstation lock when the threshold is reached.
- If the Windows lock request fails, the incident is recorded as a warning and the application-level lockout remains active.

## Security boundary

This is an application-level security shell, not a replacement for Windows Winlogon or the Windows sign-in credential provider. The next production integration phase must continue to use documented Windows security/session APIs and must never capture or proxy Windows credentials.

## Verification

Run on Windows:

```powershell
dotnet restore SmartLock.sln
dotnet build SmartLock.sln --configuration Release
dotnet test SmartLock.sln --configuration Release
```

Then run the application and test the policy with the workstation-lock checkbox disabled first. Enable it only when you are ready for Windows to lock the current session after the fifth rejected development attempt.
